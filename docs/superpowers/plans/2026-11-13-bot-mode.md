# Bot Mode Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Ship MVP Bot mode — isolated bots under `<dataDir>/bot/<name>/` that the user DMs and that talk to each other in groups via mention routing with a lead-bot facilitator.

**Architecture:** Bots bypass `AgentRouter`: one engine factory per bot, built by new isolated-engine exports in the integration packages. A shared, engine-agnostic `BotService` in `@morse/system` owns the registry, conversations, the routing middleman (N private sessions stitched by relays), and idle lifecycle. Hosts wire adapters (pi/OpenCode) and forward `bot/*` protocol messages; the Angular shell gains a Bot mode behind a new `capabilities.bot` flag.

**Tech Stack:** TypeScript, Node `node:fs` (atomic JSON writes), Vitest, Angular signals, ws (existing gateway).

**Spec:** `docs/superpowers/specs/2026-11-13-bot-mode-design.md` — read it first; this plan argues from it.

## Global Constraints

- Engine-agnostic rule: nothing in `@morse/system`'s bot module may name `pi` or `opencode`; all engine specifics live in `@morse/integration-pi` / `@morse/integration-opencode` (repo `scripts/check-agent-boundary.mjs` enforces boundaries — run `npm run lint` if it plausibly applies).
- Bot root is `<host dataDir>/bot` (`MORSE_HOME ?? ~/.morse` on the server) — never a hard-coded `~/.morse`.
- Credentials are never copied from the user's global config. Written files get mode `0600`; directories `0700`.
- Bot sessions must never write into the code-mode session store or appear in its list.
- Relay prompt format (exact): `` `[${conversationName}] ${authorLabel}: ${text}` `` where `authorLabel` is `You` for the user or the sending bot's name.
- Chain cap default `8` (`BotServiceOptions.defaultChainCap`); relay hop count includes every bot→bot delivery, never the user's own message.
- No round may exceed one in-flight prompt per bot; a `send` while a round is in flight on the same conversation is refused with a `system` transcript note.
- Idle gateway disposal default `300_000` ms (`BotServiceOptions.idleMs`).
- Tests run per package: `npm run test -w @morse/<pkg>`; UI: `npm run test -w @morse/ui-angular`. Full gate: `npm run test:fast`.

## Review Focus

The five inputs most likely to bite a real user, each pinned by a named test:

1. **Two bots on the same engine kind at once** — must get independent factories/config dirs, not collide in a kind-keyed registry. Test `two bots on one engine kind get independent gateways` (Task 5).
2. **Two bots mentioning each other forever** — chain must stop at the cap with a visible `system` note, not loop. Test `chain stops at the cap and records a capped note` (Task 5).
3. **Host restart mid-group** — conversations must resume on the stored engine session ids without duplicating sessions. Test `resume reuses stored engine session ids` (Task 5).
4. **Bad API key in the wizard** — the model probe fails with a readable reason and no bot directory is left behind. Test `createBot removes a half-written bot on probe failure` (Task 5) and `writePiCredentials overwrites without leaking partial state` (Task 3).
5. **Unknown or self mentions in a reply** (`@nobody`, a bot `@`-ing itself) — ignored with a `system` note, never a self-relay loop. Test `unknown and self mentions are ignored with a note` (Task 5).

- Round semantics (pin exactly): resolve targets — explicit mentions in order of appearance; else `all` → every member in member order; else if group has `lead` → `[lead]` with the lead's first prompt wrapped in the routing brief (exact string): `` `You are the lead of the group "${title}". Answer or @mention the teammate who should answer.` ``; else no target (append nothing, emit nothing). Per target, sequentially: ensure gateway (factory.create with stored `engineSessionId` if any, then store the new id), apply `setModel`/`setThinkingLevel` when the record has them, `prompt(`[title] You: ${text}`)`, await completion (completion = `AgentEvent` of type `agent/run-end` from that gateway — see `domain/agent/events.ts`; track the last assistant message text as the reply), append the reply as a transcript entry, then scan it: mentions of *other* members enqueue chains while `hops < chainCap` (each hop decrements; a dropped target becomes a `system` entry `Chain capped after ${chainCap} hops`). Interaction auto-answer: on `agent/interaction`, respond immediately — `confirm` → `{ requestId, confirmed: true }`; `select` → `{ requestId, value: first option's value }`; `input` → `{ requestId, value: '' }`; editor/form → `{ requestId, cancelled: true }` — and append a `system` entry `Auto-answered: ${summary}`. Reset the idle timer on every gateway activity; on expiry dispose and drop the gateway (next send re-creates and resumes via stored session id).
