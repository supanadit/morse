# Bot Bus Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Replace Bot mode's host-scheduled round with a persisted delivery bus, per-bot lanes and two bot-facing tools, so bots address each other and run in parallel.

**Architecture:** A delivery names one bot and one transcript line; a lane per bot drains deliveries in order; every transcript line is written first, so context stays the engine session plus a bounded slice pinned to the delivery's line. Two engine plugins (`pi`, `OpenCode`) expose `bot_list` and `bot_send` and call one authenticated host endpoint.

**Tech Stack:** TypeScript, npm workspaces, Vitest, NestJS (server host), Angular (UI), pi extensions, OpenCode plugins.

**Spec:** `docs/superpowers/specs/2026-11-18-bot-bus-design.md`

## Global Constraints

- `@morse/system` stays engine-agnostic: no engine names, no plugin source, no `child_process`.
- Engine knowledge lives only in `@morse/integration-pi` and `@morse/integration-opencode`.
- Protocol changes are additive: no released field changes meaning; `PROTOCOL_VERSION` bumps once per task that changes the wire.
- No user-facing setting for any backstop. No new wizard field.
- The engine session is the only context; the transcript is the only replay log. Never re-send history to build state.
- Backstops (verbatim from the spec): depth 4 per root, 48 deliveries per root, queue 32 per bot, 60 deliveries per bot per hour, 24 h undelivered TTL, 5 min turn timeout, 5 min idle gateway.
- One person, one machine. Identity is a value from `hostPerson()`; no authentication, no `owner`, no `participants`.
- Path-safe ids only: transcripts already reject anything outside `^[A-Za-z0-9_-]+$`; delivery files use the same rule.
- A dropped, refused or failed delivery always leaves a transcript note.
- Conventional commits, scope `system`, `protocol`, `server`, `ui`, `pi`, `opencode`, or `docs`.

## Review Focus

1. Two deliveries for the same bot arrive while it runs — it must queue them, run them in arrival order, and never advance `toldUpTo` past a line it did not read.
2. The bus endpoint is down (host restarting) — `bot_send` must fail with a readable error and the bot must still answer the person.
3. A bot addresses itself or a bot that was deleted mid-turn — refused or failed with a note, and the lane continues.
4. A version 2 registry on disk, plus transcripts whose author is `{ role: 'user' }` — must open, show, and read as the host person, with no rename and no loss.
5. Two bots in one room both running — the room must show both, each with its own activity and its own context ring.

- [ ] **Step 3: Implement**

- `busRoster` maps the registry to `BotRosterEntry`, with `inRoom` computed against the conversation the caller is answering in, and truncates the description to `BOT_DESCRIPTION_LIMIT`.
- `busSend` resolves the caller's current conversation from the turn file; refuses self (reason `a bot cannot send to itself`); resolves the target (in the room → deliver here; not a participant → find or create a `thread` whose members are the two bots); appends the sender's transcript line addressed to `@target`; checks `busRefusal`; adds the delivery; pumps the target's lane.
